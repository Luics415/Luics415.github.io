Tlalne-Priority

Sistema académico en C++20 para registrar, ordenar y dar seguimiento a incidencias urbanas.

Revisar repositorio

El proyecto

Tlalne-Priority modela un flujo académico de atención urbana. Registra incidencias, calcula su urgencia, conserva las finalizadas y permite consultar cada cambio sin presentarse como un sistema oficial del Ayuntamiento.

Implementación

El dominio se separa en modelos, servicios, repositorios y UI de consola. La cola de prioridad mantiene el orden operativo, mientras un índice por folio acelera búsquedas y los repositorios CSV aíslan la persistencia.

Modelo de prioridad

La puntuación combina riesgo, número de reportes, antigüedad y peso del tipo de incidencia, con un límite de 0 a 100. Se recalcula al consultar, filtrar o editar para evitar prioridades obsoletas.

Puntos destacados

  • priority_queue para recuperar primero la incidencia de mayor urgencia
  • unordered_map para localizar registros por folio sin recorrer toda la colección
  • Persistencia separada de incidencias e historial en archivos CSV
  • Compilación reproducible con CMake y prueba automatizada mediante CTest

Arquitectura técnica

El dominio se divide en modelos, servicios, repositorios y una interfaz de consola. Una cola de prioridad atiende el orden operativo, un índice por clave acelera consultas directas y la persistencia conserva registros e historial como conjuntos separados.

Flujo de ejecución

  • La entrada se valida y se transforma en un registro de dominio.
  • El servicio calcula la prioridad, actualiza el índice y coloca una referencia en la cola.
  • Las consultas recuperan por clave o prioridad y el repositorio persiste el cambio junto con su historial.

Decisiones de ingeniería

  • Combinar cola de prioridad e índice evita recorrer toda la colección para las dos consultas principales.
  • Recalcular puntuaciones dependientes del tiempo impide ordenar con valores envejecidos.
  • Aislar CSV detrás de repositorios evita contaminar las reglas de negocio con serialización.

Compromisos y límites

  • Mantener dos estructuras mejora consultas, pero obliga a sincronizarlas después de cada edición.
  • CSV es portable y auditable, aunque ofrece menos garantías transaccionales que una base de datos.
  • Una fórmula explícita es fácil de explicar, pero necesita calibración para no favorecer un único factor.

Combina riesgo, reportes, días abiertos y peso del tipo; limita las señales que podrían dominar, acota el total a 0–100 y lo traduce a una clase operativa.

Procedencia: Código real del repositorio · commit a6eb898 · services/PriorityCalculator.cpp, líneas 17–33.

int PriorityCalculator::calculate(
    const Incident& incident,
    std::chrono::system_clock::time_point now
) {
    const auto ageHours = std::max<long long>(0,
        std::chrono::duration_cast<std::chrono::hours>(
            now - incident.createdAt
        ).count());
    const int ageDays = static_cast<int>(ageHours / 24);
    const int score = incident.risk * 10
        + std::min(20, incident.citizenReports * 2)
        + std::min(15, ageDays)
        + typeWeight(incident.type);
    return std::clamp(score, 0, 100);
}

#include <algorithm>

int priorityScore(int risk, int reports, int daysOpen, int typeWeight) {
    const int raw =
        risk * 10 +
        std::min(reports * 2, 20) +
        std::min(daysOpen, 15) +
        typeWeight;

    return std::clamp(raw, 0, 100);
}
